# Opterm design interview

This document records the ongoing design interview. Decisions Q1-Q5 were accepted and explicitly preserved when switching to the grill-with-docs workflow; Q6-Q53 were subsequently accepted in their respective rounds. The subsequent user review reopened storage scope and identified missing settings and UI specification. Earlier approvals are preserved as a record; the plan is incomplete and implementation remains on hold.

## Accepted foundations

1. **Product:** A full desktop terminal for people, with a separate background session service that agents can access without opening a window.
2. **Performance:** Reduce agent workflow overhead in session startup, command dispatch, output collection, and reattachment. Reliability takes priority when speed conflicts with correctness. Measure command computation separately from Opterm's contribution.
3. **Persistence:** Live sessions survive closing or crashing the desktop application. History and workspace metadata can be restored after reboot; this does not promise restoration of arbitrary running processes after reboot or survival through session-service failure.
4. **Agents:** Support existing CLI agents and provide a provider-neutral execution API. The initial product focus is running, observing, and controlling these agents reliably.
5. **Environment:** The first release focuses on local sessions on macOS, Linux, and native Windows. SSH and container sessions are later extensions.

## Accepted implementation direction: Q6-Q13

6. **Core language:** Rust for the session service, process management, and shared core. The desktop UI toolkit remains open for evaluation.
7. **Reuse:** Build Opterm's session and agent architecture around established PTY and terminal emulation libraries. Specific libraries remain to be selected after checking compatibility, maintenance, and licensing.
8. **Execution modes:** Support interactive terminal sessions and direct command runs through the same service. Prefer direct execution when terminal interaction is unnecessary; ordinary commands can return separate stdout, stderr, and an exit result.
9. **Session ownership:** Each agent task receives its own sessions and working environment by default. People can observe without interrupting and deliberately take control; each interactive session has one active input controller. Separate sessions do not automatically provide security isolation; Q15 specifies on-demand interactive-shell creation.
10. **Agent interfaces:** Provide a versioned local API, a CLI with structured JSON output, and an MCP adapter, all sharing the session service's behavior.
11. **Desktop approach:** Target one shared desktop UI codebase with platform-appropriate shortcuts, menus, clipboard behavior, and text input. Evaluate startup, memory, rendering, accessibility, and input compatibility before selecting a toolkit.
12. **Offline operation:** Opterm works fully offline without a required account and keeps session history on the user's machine by default. Individual agents retain their own network requirements.
13. **Open source:** Make the terminal and session service open source. Q44 selects the license for Opterm-owned code; review the selected dependencies' distribution requirements separately.

## Accepted behavior and evaluation requirements: Q14-Q22

14. **Initial libraries:** Evaluate portable-pty and alacritty_terminal as the first PTY and terminal emulation candidates. They are evaluation candidates, with compatibility and performance checks required before a lasting commitment.
15. **Persistent task state:** Each task has a persistent execution context containing explicit working-directory and environment settings. Create an interactive shell only when needed; direct commands use the context, while shell-internal changes require explicit synchronization.
16. **Disconnections and uncertain results:** Reconnect to existing work when possible. Clearly report lost or unknown execution state when recovery fails, and require deliberate action before rerunning a command; a missing response must not silently cause duplicate execution.
17. **Takeover semantics:** Transfer permission to send terminal input while leaving running programs untouched. Agent API clients must reacquire control before sending more input; pausing a hosted CLI agent's internal actions requires a separate integration.
18. **History contents:** Record terminal output, direct-command invocations and results, and session/workspace metadata, with per-session recording controls. Exclude raw keystroke logs and complete environment snapshots by default; terminal output may itself contain echoed input. Q25 specifies initial output-history limits.
19. **Workspace meaning:** A workspace is a named local group of related terminal sessions and direct command runs, with a default working directory and saved desktop layout. It can represent any project or activity and does not require a Git repository or imply filesystem isolation.
20. **Local communication:** Use a versioned control protocol and chunked byte streams over same-user Unix sockets on macOS/Linux and named pipes on Windows. The CLI and MCP adapter translate results into their JSON formats; Q38 specifies initial framing, while detailed schemas remain to be designed.
21. **First desktop features:** Include multiple windows, tabs, splits, a live/detached session list, scrollback search, and keyboard navigation. Detailed workspace interaction remains to be designed.
22. **Stable-release compatibility:** Require Bash, zsh, fish, PowerShell, common full-screen terminal applications, Unicode/CJK input, and keyboard/screen-reader access to controls and terminal text. These are acceptance requirements, not claims of existing implementation coverage.

## Accepted storage, lifecycle, and evaluation decisions: Q23-Q34

23. **Storage split:** Use SQLite for task/workspace/session metadata and execution bookkeeping, with separate segmented append-only files for bulk output. Coordinate recovery and indexing across both stores; exact file formats and database settings remain to be specified.
24. **Durability contract:** Persist command acceptance before starting its effects, and persist completion bookkeeping before acknowledging completion to a client. Batch ordinary output writes, accepting that an unexpected crash or power loss can lose an unflushed tail. Distinguish command completion from transcript durability; database commits do not automatically make separate output files durable.
25. **Initial output retention:** Use configurable defaults of 30 days, 5 GiB total output-history storage, and 256 MiB per output stream. Expire the oldest retained output when limits are reached, report gaps explicitly, and leave running work untouched. Storage maintenance must respect the output cap; this is not a 5 GiB cap on all application data.
26. **Resumable output:** Use stable command/session identifiers and output byte offsets so clients can read new output and resume within retained history. Bound per-client queues so slow observers do not hold up execution, and report missed ranges. A history gap prevents a promise of complete replay.
27. **Service startup:** Start the service on demand for the current OS user and keep it alive while sessions or command runs remain active. Permit idle exit once no work remains; startup at login is optional.
28. **Initial failure boundary:** Use one session-service process initially. Its failure can end live sessions/runs, while desktop failure remains isolated. Defer per-session owner processes until measurements and failure tests justify their lifecycle and resource costs.
29. **Direct-run cancellation:** On explicit cancellation, attempt a supported graceful stop, wait up to five seconds, then force-stop the managed process tree. Make the timeout configurable; a client disconnect does not cancel work. Report uncertainty when termination cannot be verified, including processes outside the managed tree.
30. **Controller disconnect:** Release input control when its controller disconnects, without interrupting running programs. Reconnection requires an explicit claim; stale controllers cannot send input after release or takeover.
31. **Agent interface authority:** Scope API access to an assigned task and its sessions/runs, with separate observe, execute, input-control, and cancel permissions. Cross-task management requires an explicit grant. These permissions govern Opterm's interface; they do not sandbox a hosted program's OS-user privileges.
32. **UI candidates:** Compare Slint and GPUI using the same terminal-state workload and checks for rendering, startup, input methods, and screen-reader access to the custom terminal viewport. Neither is selected; review dependency terms and platform requirements before committing. Toolkit accessibility support alone does not establish accessible terminal text.
33. **Benchmark matrix:** On each target OS, compare with its native terminal, WezTerm, Alacritty, and a direct-process baseline where applicable. Match configurations at 1, 8, and 32 simultaneous sessions, using 100 as a stress scenario. Set numeric budgets from initial results and publish workload-specific conclusions; no measured speed advantage is established yet.
34. **Restored environments:** Restore working directories and explicit environment configuration, excluding complete inherited-environment snapshots and values explicitly marked secret. Inherit current host settings and require secret overrides to be supplied again after restart. This policy does not promise automatic secret detection or secret-free command/output history.

## Accepted live-state, recovery, and prototype decisions: Q35-Q47

35. **Live terminal state:** Keep authoritative live terminal state in the service, including the screen, cursor, terminal modes, and logical dimensions. Reconnecting views receive a current snapshot followed by changes; raw output remains available under Q26. Only the input controller may change session dimensions, while observers adapt their views. This adds headless parsing and state cost but avoids relying on a complete retained transcript to reconstruct the live screen.
36. **Direct-command launches:** Launch direct commands using an executable and argument array, without implicit shell parsing. Require explicit shell execution for pipelines, redirection, and shell expansion; do not promise that shell syntax or quoting is portable between operating systems.
37. **Duplicate submissions:** Give submissions stable task-scoped request IDs. Reusing an ID with the same request returns the original run; changed parameters are rejected, and expired or unrecoverable IDs return an explicit expired/unknown result instead of launching another command. The exact deduplication-retention mechanism remains an implementation design task. This does not promise exactly-once command effects through arbitrary failures.
38. **Initial wire format:** Start the local protocol with length-prefixed typed frames, JSON control payloads, and binary output payloads. Negotiate protocol versions and capabilities; reject incompatible peers with an actionable error, without automatically restarting a service that owns live work. Validate frame bounds and detailed schemas in the prototype.
39. **Storage degradation:** When output storage fails, keep existing work running, report recording degradation and history gaps, and continue live delivery where possible. Reject new command launches when their acceptance cannot be persisted. If completion bookkeeping cannot be saved, report the recording error and any known live status as unpersisted, withhold completion acknowledgement, and leave clients able to query status rather than rerun work automatically.
40. **Memory and rendering:** Bound output queues and in-memory scrollback, load older retained output on demand, and render only visible panes. Set measured service/UI memory budgets after evaluation, with admission limits for new work rather than a promise to terminate existing work to meet a memory target. CPU and memory used by hosted programs are measured separately.
41. **History protection:** Store history with access restricted to the current OS user, without application-level history encryption in the first milestone. Clearly disclose that saved output and command arguments can contain secrets, preserve recording controls, and defer optional encryption rather than promise automatic redaction.
42. **History export and deletion:** Provide deliberate export and deletion of saved history without terminating live sessions or replaying commands. An export contains a consistent metadata snapshot, referenced output, and gap information; deleting saved history does not promise erasure of a still-live screen. The portable export format and coordinated snapshot mechanism remain to be specified.
43. **Service updates:** Stage service updates until no live work remains, or until the user deliberately stops that work. Do not silently restart the service to upgrade it; the exact wire encoding does not change this update policy.
44. **Own-code license:** License Opterm-owned code under MIT OR Apache-2.0, preserving third-party licenses and notices. This does not relicense dependencies or settle which Slint licensing option would govern a Slint-based distribution; review the complete selected dependency graph before shipping.
45. **Initial native matrix:** Begin native evaluation with Apple silicon and Intel macOS, x86-64 Linux on both X11 and Wayland, and x86-64 Windows. Defer Linux/Windows ARM64; determine exact minimum OS versions and publish support claims only after the selected stack is tested.
46. **Integration milestone:** Require the first integration milestone to host at least two existing CLI agents and exercise the JSON CLI and MCP adapter with a deterministic client. Test persistence, observation, takeover, cancellation, and reconnection; distinguish hosting an unmodified agent from that agent actually adopting Opterm's execution API. Cancellation checks cover managed direct runs, and takeover checks do not imply pausing a hosted agent's internal executor. Defer provider-specific automation and language SDKs.
47. **First milestone:** Make the first milestone an evaluated Rust headless core plus comparable minimal Slint/GPUI terminal views, before building the complete desktop feature set. Include native-platform runs and failure tests, then use results to select dependencies/toolkit and set performance/resource budgets. This is a prototype plan, not permission to claim stable-release compatibility or measured superiority.

## Accepted view, inspection, and acceptance decisions: Q48-Q53

48. **View lifecycle and workspace restoration:** Treat tabs and panes as views of sessions: closing a view detaches it, while ending live work requires a separate explicit action. Workspace restoration reconnects to surviving work and shows ended/unknown work as such; it never silently reruns commands after reboot or service failure. Starting a replacement session is a deliberate action.
49. **Agent screen inspection:** Offer agents a read-only structured snapshot of the current terminal screen, including text, cell positions, cursor, dimensions, and terminal-mode information needed for inspection, alongside existing raw-output access. Require the task/session observe grant. This is a screen representation, not inferred command semantics or proof that a hosted agent has paused.
50. **Per-run context and concurrency:** Capture a direct run's working directory and effective environment at acceptance, allowing independent runs within a task to proceed concurrently. Later context changes affect later submissions, not already accepted runs; this does not serialize or isolate their filesystem effects. Keep secret values only in the live launch context, preserving Q34's persistence exclusions.
51. **Terminal-triggered desktop actions:** Require a user gesture or explicit permission for terminal-triggered clipboard reads/writes, opening links, or other desktop actions. Deny these requests by default in headless operation, while keeping ordinary terminal protocol replies available. This is a host-interaction policy, not a sandbox for the running program.
52. **Execution outcome reporting:** Report launch failure, observed program exit (including code/signal where available), cancellation request, verified managed-process termination, and unknown execution result distinctly. Track history gaps and transcript durability separately from program outcome. Requested cancellation alone must not be presented as confirmed termination, and a nonzero exit must not be presented as failure to launch.
53. **Prototype deliverables:** Deliver the prototype as runnable source and locally built artifacts where supported, plus a reproducible benchmark/failure-test report. Cover cold/warm startup, reattachment, command-dispatch overhead, output throughput, input/display latency, CPU, memory, and the agreed concurrency scenarios, with hosted computation separate. Report native platform, IME/accessibility, CLI-agent, and failure-case coverage individually, marking untested cases unverified; defer polished installers, signing/notarization, and an automatic updater until the stack is chosen. Public publication is a separate action.

## Accepted first-version and settings decisions: Q54-Q83

54. **First usable version, including standard terminal features:** Support multiple windows open simultaneously, multiple tabs, vertical and horizontal splits, renamable tabs, keyboard shortcuts, named session profiles, and custom supported profile themes. Include persistent local sessions, reattachment, existing CLI-agent hosting, a live/detached session list, copy/paste, scrollback search, essential settings, and simple local preference/layout/history files. Target macOS, Linux, and native Windows, marking untested platforms unverified. Defer SQLite, a durable direct-command ledger, public execution API/JSON CLI/MCP integration, indexed history/export, and elaborate agent management. The small internal service interface remains necessary; basic saved files do not claim the deferred durability guarantees, and service/reboot failures never trigger automatic command replay. This supersedes the proposed one-window restriction.
55. **Main-window starting layout accepted:** After rejecting the sidebar-heavy and always-three-pane PNGs, the user accepted the reference-based terminal as the starting layout: small native title bar, compact session tabs, and one continuous terminal surface. Splits remain available on demand; profiles, detached-session discovery, settings, and additional actions live in menus/shortcuts. Tighten interior padding and line spacing slightly while preserving readability and the accepted chrome. Exact numeric defaults and remaining interactions are not settled by the PNG.
56. **Reference-led visual direction accepted, with standalone styling:** Follow the user's thin native-terminal reference and approved compact refinement as the layout baseline. The later instruction to exclude anything Crateon-related supersedes the earlier typography/palette reuse request: choose independent fonts, neutral themes, and Opterm-owned styling. Do not continue the unselected A/B/C proposals or force prominent branding. Exact numeric defaults, field behavior, cross-platform decorations, and an embedded Chat/Diff/Code Review feature set are not settled by the PNG.
57. **Settings model:** Provide a settings UI and readable TOML describing the same settings. Use global preferences and named session profiles for shell/agent launch settings, retaining workspace working directories and deferring general configuration inheritance. Support custom profile themes as the explicitly requested limited appearance override. Appearance, keyboard/clipboard, profiles, and session/history behavior are the initial groups; detailed fields, defaults, validation, and application timing remain open.
58. **Settings presentation:** Use a compact separate settings window with Appearance, Shortcuts & clipboard, Profiles, and Sessions & history. Keep settings outside the ordinary terminal view.
59. **Appearance scope:** Keep font, font size, horizontal/vertical padding, terminal line height, and application theme global initially. Session profiles may select their own terminal color themes, including custom supported colors. Do not introduce general per-profile font/spacing inheritance; preserve blank rows and indentation emitted by hosted programs. Exact numeric defaults and supported theme fields remain to be specified.
60. **Quick session/profile access:** Clicking plus opens a new session using the default profile; a small adjacent dropdown offers other profiles. A compact session picker reattaches existing live/detached sessions rather than restarting their programs. Splits, tab renaming, and new-window actions remain available through menus and keyboard shortcuts; detailed key bindings and window/tab behavior remain open.
61. **Shortcut behavior:** Provide customizable platform-appropriate defaults and reset-to-default controls. Preserve ordinary shell keys unless deliberately rebound. Flag duplicate app bindings and require an explicit reassignment rather than silently overriding another action.
62. **Tab/window interaction:** Support drag reordering, moving tabs between windows, and dragging a tab out to create a window. Preserve its live sessions, split layout, and manual names without restarting hosted programs; manual names remain until explicitly changed/reset.
63. **Applying settings:** Apply saved appearance and shortcut changes immediately. Changes to launch-profile program/directory/environment settings affect newly started sessions, leaving existing shells and agents running. Edits to a terminal theme update the views using it without restarting their programs. Save/cancel and concurrent GUI/file editing remain to be specified.
64. **Invalid configuration and recovery backup:** Keep the last valid settings after an invalid TOML edit, show a useful error and file location, and apply the configuration once corrected. Preserve a recoverable last-valid global-settings snapshot separately from the editable configuration, in the current user's app-data/state location with user-only access. Validate before updating it; write safely so an interrupted/failed replacement keeps the previous good snapshot, and never replace it with invalid data. Make recovery available from settings and use the snapshot if startup configuration is missing/corrupt, explaining the recovery without silently overwriting the user's file. With no valid file or backup, use built-in defaults with an explicit notice. Respect the existing exclusions for marked secret values; backup failures must be reported rather than claiming a recoverable save. This is configuration recovery, not a promise to preserve running processes.
65. **Startup experience:** Restore the last window/tab/split layout and reattach surviving sessions by default. Show ended/unknown sessions without restarting their commands; restoration never silently replays work. On a fresh setup, open one session using the default shell profile. Allow restoration to be disabled.
66. **Profile management:** Provide create, duplicate, rename, edit, delete, and choose-default controls for named shell/agent profiles. Each specifies a name, executable/arguments, starting directory, explicit environment overrides, and terminal theme. Deleting a preset does not end sessions already launched with it. Directory and deleted-default fallbacks remain to be specified.
67. **Custom themes, with standalone presets:** Provide neutral Dark and Light presets, custom terminal foreground/background, cursor, selection, and 16 ANSI colors, a settings color editor, and TOML theme import/export. The user's qualifier explicitly excludes Crateon-related presets, branding, token/code dependencies, and integrations. Fonts, spacing, and application chrome remain global; themes contain supported color data rather than executable plugins.
68. **Settings editing:** Use an editable draft with Save/Cancel. Validate before saving, apply accepted changes according to Q63, and maintain Q64's recovery backup. Validate external TOML changes before applying them. If the file changes while a GUI draft is open, require reload or an explicit decision to replace it rather than silently overwriting edits. Detailed labels and save-failure behavior remain for the settings review.
69. **Compact appearance defaults:** Use the platform's available system monospace font, 14 px text, 6 px terminal padding, and 1.2 line spacing, all adjustable. Include independent neutral Dark/Light themes and system-following application chrome. These are accepted starting defaults, not measured optimums; exact font fallback and DPI behavior remain implementation details.
70. **Custom settings/cache locations:** The user clarified their directory requirement as a custom location for the terminal's settings and cache. Support user-selected storage locations. Q73 subsequently settles the base-folder structure; relocation behavior remains open. The original shell starting-directory question was separate and is subsequently settled by Q75. Cache is recreatable application data, distinct from settings, saved history, live sessions, and the protected recovery copy.
71. **Split controls:** Support pointer/keyboard resizing and pane focus, temporarily maximizing one pane, and restoring its previous split layout. Closing a pane detaches its view; ending the session remains a separate action. Exact shortcuts remain to be specified.
72. **Deleted defaults:** Fall back to a built-in default-shell profile when the selected default profile is deleted, and a built-in neutral theme when a referenced custom theme is deleted. Explain changed selections and leave running programs uninterrupted. Detailed live-session handling remains to be specified.
73. **Custom folder structure:** Use one user-selected Opterm folder with separate settings/ and cache/ subfolders. Provide a folder picker and remember the location for startup. Keep the protected recovery copy separately in the user's normal app-data/state location, outside cache. Folder relocation and unavailable-path behavior remain to be specified.
74. **Cache clearing:** Provide a Clear cache action that removes only recreatable application cache, preserving settings, profiles, themes, saved history, workspace layout, recovery backups, and live sessions. Cache cleanup must respect those boundaries.
75. **Shell starting directories:** An explicit profile directory takes priority, followed by the workspace default, then home when neither is configured. An unavailable configured directory produces an actionable error rather than silently launching somewhere else. This is distinct from the selected settings/cache storage folder.
76. **Changing storage location:** Copy validated settings to the chosen folder, preserve the originals, and activate the new location on the next desktop launch. Recreate cache there, leave the recovery copy separate, and preserve service-owned live sessions. Report an unavailable location and offer another location/recovery rather than silently changing the choice; do not restart the session service for this change.
77. **Clipboard behavior:** Use explicit copy/paste by default, with optional copy-on-select disabled initially. Preserve Ctrl+C as terminal interrupt unless deliberately rebound. Use platform-appropriate copy/paste shortcuts; terminal-triggered clipboard requests remain subject to Q51.
78. **Scrollback and recording:** Start with 10,000 live scrollback lines per session, configurable and with a separate memory/byte bound to be set from evaluation. Save output by default with per-session recording controls, retaining Q25's 30-day/5-GiB-total/256-MiB-stream saved-output limits. Live scrollback and disk history are distinct; pruning or clearing saved output does not terminate work. First-version history remains simple files without indexed history/export or a command ledger.
79. **Settings layout accepted:** Use the compact standalone four-tab settings layout shown in the Appearance PNG, with accepted defaults, Save/Cancel, configuration access, and recovery action. Follow native control conventions on each platform. The PNG establishes design direction, not precise renderer dimensions, functional behavior, accessibility results, or benchmark evidence.
80. **Shortcut defaults:** Use Cmd+T/N/W/C/V/F on macOS for new tab, new window, close view, copy, paste, and search respectively; use Ctrl+Shift+the same letter on Windows/Linux. Split right uses Cmd+D / Ctrl+Shift+E; split below uses Cmd+Shift+D / Ctrl+Shift+O. These are editable Opterm defaults, with conflict checks under Q61.
81. **Automatic tab titles:** Use the program-supplied terminal title when available, with the profile name as fallback. A manual name takes priority until explicitly reset to automatic, including after movement and reattachment.
82. **New split profile:** Start a new split with the default profile, with another profile selectable through the split menu. Use Q75's directory precedence. Each split starts a separate session rather than duplicating a running process.
83. **Paste behavior:** Preserve pasted text and line breaks without appending an extra Enter. Embedded newlines are handled by the shell or running program. Terminal paste-protocol compatibility remains an implementation task.

The user's screenshot and compact refinement establish the accepted layout. Earlier other-product design references are superseded and are not dependencies or shipping assets. The application uses independent neutral styling. The [UI/settings specification](ui-settings-spec.md) captures the current direction; [the glossary](../GLOSSARY.md) defines session profiles and profile themes.
